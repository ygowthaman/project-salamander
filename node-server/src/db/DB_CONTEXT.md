# DB Context

This folder handles all database connectivity and query logic for the Salamander backend.

## Database

PostgreSQL, accessed through Drizzle ORM over `pg` (node-postgres). In local dev it is a locally installed PostgreSQL 16. In production it is a self-managed PostgreSQL on a Compute Engine VM, reached from Cloud Run over Direct VPC egress — see `docs/DEPLOYMENT.md` for the as-built topology.

## Dependencies

`client.ts` is the single dependency point for the rest of the backend. It owns the `pg.Pool` and the Drizzle instance built on top of it. Because `pg` pools connections internally, there is no session factory and no request-scoped dependency injection to wire up — callers import `db` directly and the pool hands out a connection per query.

Repositories accept a `DbExecutor` — either the pool-backed `db` or a transaction handle from `db.transaction(...)`. That one type is what lets the same repository function be called inside or outside a transaction, which the interpret-and-commit flow relies on to write a row and its audit event atomically (see `../api/API_CONTEXT.md`).

Keep transactions off the LLM path: never hold one open across a call to Anthropic, or a pooled connection stays pinned for the length of a network round trip.

`DATABASE_URL` is normalised in `client.ts`: the old SQLAlchemy `postgresql+asyncpg://` scheme is rewritten to plain `postgresql://`, so a stale `.env` still works.

## Migrations

Schema changes are versioned SQL files in `../../drizzle/`, generated by `drizzle-kit generate` from `schema/` and applied by `migrate.ts` on server startup. This replaces SQLAlchemy's `Base.metadata.create_all`, which created missing tables but could never alter existing ones.

After editing `schema/`, run `npm run db:generate` and commit the generated SQL — do not hand-edit a migration that has already been applied anywhere.

The household migration is a case `db:generate` cannot write on its own. Turning `user_id` into `household_id` on the domain tables needs a data step between the DDL — add `households`, insert one row per existing user, add the nullable FKs, backfill from the old `user_id`, then set NOT NULL and drop the old column. While nothing holds data worth keeping, the generated drop-and-recreate is fine and this is a note for whoever runs it after that stops being true (see the `--reset` discussion under `migrate.ts`).

## Why the schema is a folder, and the version floor it needs

`schema/` is split one module per domain rather than one big file, so the module boundaries are enforced by imports instead of by comments — see the table under *Files*.

**This requires `drizzle-kit >= 0.31`, which in turn requires `drizzle-orm >= 0.45`.** The reason is worth keeping, because the failure is obscure:

- The project is `"type": "module"` with `moduleResolution: NodeNext`, so a relative import **must** carry a `.js` extension (`import { users } from "./auth.js"`). Node's ESM resolver rejects the extensionless form at runtime, so there is no way to write these imports that avoids it.
- drizzle-kit 0.28.1 loaded the schema through CJS `require`, which resolved `./auth.js` literally, found no such file, and failed `db:generate` with `MODULE_NOT_FOUND`. A single-file schema never hit this only because it had no relative imports.
- A `schema/*.ts` glob does not dodge it: each module still imports its foreign-key targets, because `references(() => categories.id)` needs the real table object. Cross-file imports are unavoidable in a split schema.

So: **do not downgrade drizzle-kit without collapsing this folder back into one file.** The symptom would be a `MODULE_NOT_FOUND` naming a schema module during `db:generate`, which reads like a missing file rather than a version problem.

The related upgrade note: `drizzle-orm` 0.45 changed the `pgTable` `extraConfig` callback to return an **array** of indexes rather than an object keyed by name. The object form still compiles as a deprecated overload; every table here uses the array form. Index names were always explicit strings, so nothing was lost in the move.

## Households: the ownership root

**A household owns the data; a user owns only their credentials.** Every domain table carries `household_id`, not `user_id`. `users` carries a NOT NULL FK to `households`, and that FK is the *only* path from a person to anything they can see.

The reason is that the product's aggregates are per-home, not per-person. Two people in one house share one pantry: if `inventory_items` were scoped per user, the same carton of eggs would exist as two rows with two counts, a mandate would fire against one of them, and a budget would total a household's spend at half its real value with nothing erroring. That is the same failure mode the `categories` table exists to prevent — drift that escapes the row and corrupts an aggregate — applied one level up.

**Household creation is optional at the product level and mandatory at the schema level.** A user who never creates one is given a single-member household in the same transaction as the account insert. Because UUIDs are app-generated (`crypto.randomUUID`), the household id is known before either row is written, so this is one transaction with no nullable-then-backfill window and no deferred constraint.

**An auto-provisioned household is not marked as such, and that is the point.** There is no `is_personal` flag and no "upgrade" path. "Creating a household" in the UI is a rename plus an invite against a row that already exists — never a data migration that re-parents a user's inventory. A flag would immediately grow branches (what happens to a personal household that gains a second member?) to describe a distinction the schema does not need.

`households` holds `id`, a NOT NULL `name`, and a nullable `address`. The name is mandatory because it is what the UI calls the scope in every list and header; auto-provisioning derives one (`"<display name>'s Household"`, falling back to the email local part) rather than allowing null. The address is nullable because nothing reads it yet — it is there for Phase 2 delivery, and until then it is a free-text field, not a joined-on one (see the conventions below).

**One household per user, one FK, no join table.** A user belongs to exactly one household. If multi-household membership is ever needed, the change is a `household_members` join table with `users.household_id` demoted to "currently active household" — additive, and deliberately not built now.

**`households` imports nothing, and must not.** It is the new root of the dependency graph, above `auth`. In particular, **do not add an owner or creator FK from `households` to `users`** — that closes a cycle with `users.household_id`, which Drizzle's lazy `references(() => x.id)` would let survive at runtime while TS inference degrades. Anything that expresses a person's relationship to a household belongs on the user side.

**The auth tables stay on `user_id`.** `oauth_accounts` and `auth_sessions` are credentials and login state — they describe the person, not the home, and a refresh token has no household. The rule is not "no table references `users` any more"; it is that **no *domain* table does**.

Deletes:

- `users.household_id` is `ON DELETE RESTRICT`. Deleting a household that still has members is a 409, not a cascade that would orphan or delete people.
- Domain tables are `ON DELETE CASCADE` on `household_id`, so deleting an emptied household takes its data with it.
- Deleting a *user* no longer cascades their data away — the household outlives them, which is the correct behaviour for a shared pantry and the main behavioural change from the old `user_id` model. The corollary is that **account deletion is no longer a single `DELETE FROM users`**: it must delete the household too when the leaving member was the last one, or the row and its inventory are orphaned with nothing able to reach them. That check belongs in `repositories/households.ts`, in the same transaction, because a `RESTRICT` FK cannot express "cascade only if last".

## Files

- **client.ts** — `pg.Pool` + Drizzle instance, and the `Db` / `DbExecutor` types. Everything else in this folder depends on it.

- **schema/** — Drizzle table definitions and the inferred row types, one module per domain. `sessions` and `messages` went with the chat app, dropped by `drizzle/0002_drop_chat.sql`.

  | File | Tables |
  |---|---|
  | `common.ts` | no tables — the `createdAt()` / `updatedAt()` column helpers |
  | `households.ts` | `households` |
  | `auth.ts` | `users`, `oauth_accounts`, `auth_sessions` |
  | `categories.ts` | `categories` |
  | `inventory.ts` | `inventory_items`, `inventory_events` |
  | `mandates.ts` | `mandates` |
  | `index.ts` | the barrel — re-exports every table module |

  **Import direction is load-bearing, not cosmetic.** The graph is acyclic and must stay so: `households ← auth ← categories ← inventory ← mandates`. Two invariants sit on it:

  - **`households.ts` imports nothing.** It is the root. An owner FK back to `users` would close a cycle — see *Households* above.
  - **`inventory.ts` must never import `mandates.ts`** — decision D1 says the inventory module has no knowledge of reordering, and as separate files that invariant is greppable rather than merely written down.

  Every domain module now imports `households.ts` for its `household_id` FK, and `auth.ts` imports it for `users.household_id`. **No module outside `auth.ts` imports `auth.ts` any more** — a domain module reaching for `users` is the signal that something is being scoped per person instead of per household. Drizzle's `references(() => x.id)` is lazy, so a cycle would survive at runtime while TS inference quietly degrades; if two modules ever need each other, the tables probably belong together.

  **Both drizzle-kit and `client.ts` enter through `index.ts`.** `drizzle.config.ts` points at the barrel rather than a `schema/*.ts` glob, so the set of tables in migrations is by construction the set `db.query` can see. A glob would let the two drift.

  **The operative model for the domain tables is `docs/context/INVENTORY_CONTEXT.md` §2, not `docs/PRD.md` §6.** The PRD puts `par_level` / `restock_level` on `inventory_items`; decisions D1 + D4 moved them onto `mandates` and the PRD is knowingly stale until its reconciliation pass. Read the divergence banner there before changing any of these tables back to match it.

  Quantity columns (`quantity`, `delta`, `new_stock`, `par_level`, `restock_level`) are **`integer`**, not the fractional value PRD §5.1 describes (decision D5). `unit` is user-defined free text, so the user picks the granularity at which things are whole: half a dozen eggs is `6 × each`, not `0.5 × dozen`. The cost is that a part-used package has no whole number — a half-eaten bag counts as `1`, so its reorder fires one cycle late — which is acceptable for a number that feeds a threshold comparison and a table the user reads.

  Because `pg` parses `int4` directly to a JS `number`, there is no string round-trip and repositories need no parsing layer. **That changes if a `numeric` column is ever added** (money on `budgets` is the likely first): `pg` returns `numeric` as a *string* to avoid float precision loss, and converting it is then a deliberate per-column decision, not a global type-parser override.

- **migrate.ts** — runs pending migrations. Called by `server.ts` at boot; also runnable standalone.

  **`npm run db:migrate` passes `--reset`: it drops every table in `public`, drops drizzle's `drizzle.__drizzle_migrations` bookkeeping schema, and replays the chain from empty.** This is deliberate for the current phase and safe only because no database holds data worth keeping. The reason it is the default rather than an opt-in: the migrator keys on a *hash of each SQL file*, so while the schema is still being drafted — squashing the baseline, amending a table before anything ships — every edit to an applied migration leaves that database permanently stuck, re-running a "pending" file against tables that already exist. Recovering by hand costs more than a wipe.

  `npm run db:migrate:preserve` is the same script without the flag: apply pending migrations, drop nothing. Use it the moment a database holds anything you would mind losing.

  **Server startup never drops.** `runMigrations()` is the only thing `server.ts` imports; `resetSchema()` is reachable only from the CLI branch, only under `--reset`, and refuses outright when `NODE_ENV=production`. The script prints the target `host:port/database` before dropping, because the failure mode that matters here is a `.env` pointed somewhere other than local Postgres.

  **Flip the default to `db:migrate:preserve` before any database holds real data** — that is the switch this arrangement is waiting on, not a cleanup someone will notice on their own.

- **repositories/** — query logic, one module per table. The chat repositories (`sessions.ts`, `messages.ts`) are gone; the domain repositories join the auth ones below.

- **repositories/users.ts** — query logic for `users`. Owns email normalisation (lowercasing) so a caller cannot forget and create a case-duplicate account.

- **repositories/oauthAccounts.ts** — provider identity links, keyed on the provider's stable subject id rather than email. See `../auth/AUTH_CONTEXT.md`.

- **repositories/authSessions.ts** — refresh-token records and revocation. `getByRefreshHash` deliberately returns revoked and expired rows so the refresh route can tell an unknown token from a replayed one.

- **repositories/households.ts** — the household row plus the create-account-and-household transaction. Auto-provisioning lives here, not in the auth routes, so that *no* code path can insert a `users` row without a household.

The scoping habit the deleted chat repositories established stays, one level up: every read on a domain table takes the **household id** as an argument, and there is intentionally no unscoped lookup to reach for. The auth repositories keep taking a user id, because their tables are still user-owned.

The binding rule moves with it. `household_id`, like `user_id` before it, is **resolved server-side from the authenticated session** — never read from a request body and never from an LLM response. The interpreter is handed the household's `{id, name}` category pairs and returns a `category_id`; it is never told the household id and has no way to name one. (`docs/ARCHITECTURE.md` and `CLAUDE.md` still phrase this invariant as "`user_id` is bound server-side" — same rule, pre-household wording.)

## Conventions for new tables

- **App-generated UUID primary keys** via `crypto.randomUUID` rather than a DB-side `gen_random_uuid()`, so no `pgcrypto` extension is needed and the ID is known before the insert returns. Household auto-provisioning depends on this — see *Households*.
- **Every domain table carries `household_id UUID NOT NULL REFERENCES households(id) ON DELETE CASCADE`**, indexed as `(household_id, …)` for its common list query. A new domain table referencing `users(id)` is a bug, not a variation: only `oauth_accounts` and `auth_sessions` do that, because they are credentials.
- **Attribution is a separate column from ownership.** Where "who did this" is worth keeping — `inventory_events` is the case that exists today — the row carries both `household_id` (the scope every query filters on) and a nullable `actor_user_id REFERENCES users(id) ON DELETE SET NULL` (the person, for display only). `SET NULL` rather than `CASCADE`: a departing housemate must not delete the household's stock history. Never filter on `actor_user_id`; it is provenance, the same way `inventory_events.reason` is.
- **`jsonb` only for genuinely open-ended fields** (item `attributes`, fallback decisions, notification payloads), validated with zod at the boundary. Anything queried or constrained gets a real column.
- **Anything the app joins on is its own table, not a string column.** `categories` is the worked example (`docs/PRD.md` §5.1.1): budgets aggregate spend by category, so as free text an interpreter writing `grocery` one day and `groceries` the next would silently split a budget with nothing erroring. It carries `UNIQUE (household_id, lower(name))` — a household shares one taxonomy, so two members cannot each create "Groceries" — and both `inventory_items.category_id` and `budgets.category_id` reference it `ON DELETE RESTRICT`, making deletion of a category with items a 409 rather than a cascade that would take a whole collection with it. Apply the same test before adding any other classification column: **does anything join on it, and does drift escape the row?** `inventory_items.unit` fails both, so it stays free text; `households.address` fails both today for the same reason.
