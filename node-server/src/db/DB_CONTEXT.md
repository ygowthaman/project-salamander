# DB Context

This folder handles all database connectivity and query logic for the Salamander backend.

## Database

PostgreSQL, accessed through Drizzle ORM over `pg` (node-postgres). In local dev it is a locally installed PostgreSQL 16. In production it is a self-managed PostgreSQL on a Compute Engine VM, reached from Cloud Run over Direct VPC egress — see `docs/DEPLOYMENT.md` for the as-built topology.

## Dependencies

`client.ts` is the single dependency point for the rest of the backend. It owns the `pg.Pool` and the Drizzle instance built on top of it. Because `pg` pools connections internally, there is no session factory and no request-scoped dependency injection to wire up — callers import `db` directly and the pool hands out a connection per query.

Repositories accept a `DbExecutor` — either the pool-backed `db` or a transaction handle from `db.transaction(...)`. That one type is what lets the same repository function be called inside or outside a transaction, which the interpret-and-commit flow relies on when one sentence names several items and either all of them land or none do (see `../api/API_CONTEXT.md`).

Keep transactions off the LLM path: never hold one open across a call to Anthropic, or a pooled connection stays pinned for the length of a network round trip.

## Migrations

Schema changes are SQL files in `../../drizzle/`, generated by `drizzle-kit generate` from `schema/` and applied by `migrate.ts` on server startup. Generated files rather than create-tables-on-boot, because the latter can create a missing table but can never alter an existing one.

**For the current phase the schema is not versioned — it is republished.** Both halves of the cycle throw everything away and rebuild from `schema/`:

- `npm run db:generate` deletes the whole `drizzle/` folder (`reset-migrations.ts`), then regenerates one baseline `0000_init.sql`.
- `npm run db:migrate` drops every table in `public` plus drizzle's bookkeeping schema, then replays that baseline into an empty database.
- `npm run db:reset` is the two in order, which is the normal way to pick up a schema edit.

So the loop after editing `schema/` is: `npm run db:reset`, then commit the regenerated SQL. There is no such thing as a migration that has already been applied somewhere, and therefore nothing to hand-edit or catch up — a mistake is fixed by changing `schema/` and rebuilding. **This holds only while no database holds data worth keeping**; see the switch note under `migrate.ts`.

Two things fall out of the wipe that are worth knowing, because both were real costs before it:

**Generation is now non-interactive.** drizzle-kit cannot tell a rename from a create+drop and asks — through a prompt that requires a real TTY and aborts under piped input or CI with `Interactive prompts require a TTY terminal`. The household change hit this on every domain table at once, each dropping `user_id` and adding `household_id` in one diff. Against an empty `drizzle/` every table is a plain create, so there is no ambiguity left to prompt about and `db:generate` runs unattended.

**Nothing needs a data step, because there is no data.** A real `user_id` → `household_id` migration is not DDL alone: add `households`, insert one row per existing user, add the nullable FKs, backfill, then set NOT NULL and drop the old column. Rebuilding from empty skips all of it. That is the single largest thing the republish model is spending, and the reason the switch below is not a cleanup to defer.

## Why the schema is a folder, and the version floor it needs

`schema/` is split one module per domain rather than one big file, so the module boundaries are enforced by imports instead of by comments — see the table under *Files*.

**This requires `drizzle-kit >= 0.31`, which in turn requires `drizzle-orm >= 0.45`.** The reason is worth keeping, because the failure is obscure:

- The project is `"type": "module"` with `moduleResolution: NodeNext`, so a relative import **must** carry a `.js` extension (`import { users } from "./auth.js"`). Node's ESM resolver rejects the extensionless form at runtime, so there is no way to write these imports that avoids it.
- drizzle-kit 0.28.1 loaded the schema through CJS `require`, which resolved `./auth.js` literally, found no such file, and failed `db:generate` with `MODULE_NOT_FOUND`. A single-file schema never hit this only because it had no relative imports.
- A `schema/*.ts` glob does not dodge it: each module still imports its foreign-key targets, because `references(() => categories.id)` needs the real table object. Cross-file imports are unavoidable in a split schema.

So: **do not downgrade drizzle-kit without collapsing this folder back into one file.** The symptom would be a `MODULE_NOT_FOUND` naming a schema module during `db:generate`, which reads like a missing file rather than a version problem.

The related upgrade note: `drizzle-orm` 0.45 changed the `pgTable` `extraConfig` callback to return an **array** of indexes rather than an object keyed by name. The object form still compiles as a deprecated overload; every table here uses the array form. Index names were always explicit strings, so nothing was lost in the move.

## Households: the ownership root

**A household owns the data; a user owns only their credentials.** Every domain table carries `household_id`, not `user_id`. `users` carries a NOT NULL FK to `households`, and that FK is the *only* path from a person to anything they can see.

The reason is that the product's aggregates are per-home, not per-person. Two people in one house share one pantry: if `inventory_items` were scoped per user, the same carton of eggs would exist as two rows with two counts, a mandate would fire against one of them, and a budget would total a household's spend at half its real value with nothing erroring. That is the same failure mode the `categories` table exists to prevent — drift that escapes the row and corrupts an aggregate — applied one level up.

**Household creation is optional at the product level and mandatory at the schema level.** A user who never creates one is given a single-member household in the same transaction as the account insert. Because UUIDs are app-generated (`crypto.randomUUID`), the household id is known before either row is written, so this is one transaction with no nullable-then-backfill window and no deferred constraint.

**An auto-provisioned household is not marked as such, and that is the point.** There is no `is_personal` flag and no "upgrade" path. "Creating a household" in the UI is a rename plus an invite against a row that already exists — never a data migration that re-parents a user's inventory. A flag would immediately grow branches (what happens to a personal household that gains a second member?) to describe a distinction the schema does not need.

`households` holds `id`, a NOT NULL `name`, a nullable `address`, and the timestamps. The name is mandatory because it is what the UI calls the scope in every list and header; auto-provisioning derives one from **the local part of the user's email** — everything before the `@` — rather than allowing null. The email and not the display name, deliberately: PRD §2.2.5 points out that email is mandatory on every account while the display name is optional, so only the email is guaranteed to give the derivation an input. The address is nullable because nothing reads it yet — it is there for Phase 2 delivery, and until then it is a free-text field, not a joined-on one (see the conventions below).

### What the user side carries

Three columns on `users` exist only because of the household model, and each is on the person rather than on `households` for the reason above — the root table must not point back.

- **`household_id`** — NOT NULL, `ON DELETE RESTRICT`. The membership itself, and the only path from a person to anything they can see.
- **`role`** — a `user_role` pgEnum of `admin` / `user` (PRD §2.3). On the user because a user belongs to exactly one household, so "their role" and "their role in that household" coincide; **if multi-household membership is ever built, this column moves onto the join table with the membership.** Defaulted to `user` so a call site that forgets cannot mint an administrator, though every insert path states it explicitly. Note that this is the first `pgEnum` in the schema — `resetSchema()` in `migrate.ts` already drops enum types, and now actually has one to drop.
- **`skip_household`** — whether the household was provisioned silently (`true`) or deliberately created/joined (`false`). The *data* is identical in both cases; this records the user's **understanding**, and it is what lets the UI avoid showing household features to someone who does not know they have one. It is **not** a "has the form been shown" flag: a user who skipped and a user who was never asked both sit at `true`, so the form is triggered by account creation (both sign-up routes report it) and this records the answer.

### Soft delete, and why `users` rows outlive their accounts

`users.deleted_at` marks a retired account (PRD §2.2.8). The row survives for exactly one reason — inventory attribution — and everything else about the account is destroyed in the same transaction: password nulled, provider links deleted, sessions revoked.

**The email is released by overwriting it, not by relaxing the index.** A soft delete replaces the address with `deleted-<id>@salamander.invalid`. `.invalid` is reserved by RFC 2606 and can never be a real address, so the plain unique index goes on constraining active accounts only — no partial index, and `email` stays NOT NULL for every path that reads it. This matches the PRD's stronger requirement that the address is *discarded outright, not held in reserve*, which a `WHERE deleted_at IS NULL` index would not satisfy: it would keep the old address readable in the row.

`repositories/users.ts` filters `deleted_at IS NULL` in `getUserById` and `getUserByEmail`, so the auth plugin cannot resolve a request onto a retired record. `getUserByIdIncludingDeleted` is the deliberate exception, for rendering a departed member's name — never for authentication and never for membership.

**One household per user, one FK, no join table.** A user belongs to exactly one household. If multi-household membership is ever needed, the change is a `household_members` join table with `users.household_id` demoted to "currently active household" — additive, and deliberately not built now.

**`households` imports nothing, and must not.** It is the new root of the dependency graph, above `auth`. In particular, **do not add an owner or creator FK from `households` to `users`** — that closes a cycle with `users.household_id`, which Drizzle's lazy `references(() => x.id)` would let survive at runtime while TS inference degrades. Anything that expresses a person's relationship to a household belongs on the user side.

**The auth tables stay on `user_id`.** `oauth_accounts` and `auth_sessions` are credentials and login state — they describe the person, not the home, and a refresh token has no household. The rule is not "no table references `users` any more"; it is that **no *domain* table does**.

Deletes:

- `users.household_id` is `ON DELETE RESTRICT`. Deleting a household that still has members is a 409, not a cascade that would orphan or delete people.
- Domain tables are `ON DELETE CASCADE` on `household_id`, so deleting an emptied household takes its data with it.
- Deleting a *user* no longer cascades their data away — the household outlives them, which is the correct behaviour for a shared pantry and the main behavioural change from the old `user_id` model. The corollary is that **account deletion is not a single statement**: it retires the account, and it must dissolve the household too when the leaving member was the last **admin**, or the row and its inventory are left with nothing able to reach them. That check cannot be a `RESTRICT` FK — no foreign key expresses "only if last" — so it lives in `repositories/households.ts` → `deleteAccount`, inside the transaction.
- **Order matters when a household is destroyed: inventory, then occupants, then the household row.** Two RESTRICT foreign keys fix it. `inventory_items.added_by_user_id` is `NOT NULL … RESTRICT`, so nobody can be moved off the household while its items still attribute to them; `users.household_id` is `RESTRICT`, so the household row cannot go while anyone still points at it. Get the order wrong and the delete fails with a foreign-key violation rather than doing half the work. Whatever is left hangs off the household by `CASCADE`, so dropping that row takes the categories and anything else with it.
- **Destroying a household destroys its data, not its people.** Every occupant — retired accounts included, since a soft-deleted row still holds the RESTRICT above — is moved into a silent household of its own rather than deleted (PRD §2.2.8). No operation in the product hard-deletes a `users` row.

## Files

- **client.ts** — `pg.Pool` + Drizzle instance, and the `Db` / `DbExecutor` types. Everything else in this folder depends on it.

- **schema/** — Drizzle table definitions and the inferred row types, one module per domain. There is no conversational storage of any kind, and no migration is needed to say so: the `sessions` and `messages` tables the retired Python backend created are not in `schema/`, so `db:migrate` drops them with everything else in `public` and never recreates them. (A `0001_drop_legacy_chat_tables.sql` used to carry that; it is redundant under the wipe and disappears at the next `db:generate`.)

  | File | Tables |
  |---|---|
  | `common.ts` | no tables — the `createdAt()` / `updatedAt()` column helpers |
  | `households.ts` | `households` |
  | `auth.ts` | `users`, `oauth_accounts`, `auth_sessions` |
  | `categories.ts` | `categories` |
  | `inventory.ts` | `inventory_items` |
  | `mandates.ts` | `mandates` |
  | `index.ts` | the barrel — re-exports every table module |

  **Import direction is load-bearing, not cosmetic.** The graph is acyclic and must stay so: `households ← auth ← categories ← inventory ← mandates`. Two invariants sit on it:

  - **`households.ts` imports nothing.** It is the root. An owner FK back to `users` would close a cycle — see *Households* above.
  - **`inventory.ts` must never import `mandates.ts`** — decision D1 says the inventory module has no knowledge of reordering, and as separate files that invariant is greppable rather than merely written down.

  Every domain module imports `households.ts` for its `household_id` FK, and `auth.ts` imports it for `users.household_id`.

  **The rule about `auth.ts` is "no domain table takes its *scope* from `users`", not "nothing imports `auth.ts`".** `inventory.ts` does import it, and is the only domain module that may: `inventory_items.added_by_user_id` is attribution and privacy (PRD §2.2.9), `NOT NULL … ON DELETE RESTRICT`, and never the row's owner. A domain module importing `auth.ts` for an owner column is the bug this rule exists to catch — grep for `references(() => users.id` and check each hit is that shape. Drizzle's `references(() => x.id)` is lazy, so a cycle would survive at runtime while TS inference quietly degrades; if two modules ever need each other, the tables probably belong together.

  **Both drizzle-kit and `client.ts` enter through `index.ts`.** `drizzle.config.ts` points at the barrel rather than a `schema/*.ts` glob, so the set of tables in migrations is by construction the set `db.query` can see. A glob would let the two drift.

  **The operative model for the domain tables is `docs/context/INVENTORY_CONTEXT.md` §2, not `docs/PRD.md` §6.** The PRD puts `par_level` / `restock_level` on `inventory_items`; decisions D1 + D4 moved them onto `mandates` and the PRD is knowingly stale until its reconciliation pass. Read the divergence banner there before changing any of these tables back to match it.

  Quantity columns (`quantity`, `par_level`, `restock_level`) are **`integer`**, not the fractional value PRD §5.1 describes (decision D5). `unit` is user-defined free text, so the user picks the granularity at which things are whole: half a dozen eggs is `6 × each`, not `0.5 × dozen`. The cost is that a part-used package has no whole number — a half-eaten bag counts as `1`, so its reorder fires one cycle late — which is acceptable for a number that feeds a threshold comparison and a table the user reads.

  Because `pg` parses `int4` directly to a JS `number`, there is no string round-trip and repositories need no parsing layer. **That changes if a `numeric` column is ever added** (money on `budgets` is the likely first): `pg` returns `numeric` as a *string* to avoid float precision loss, and converting it is then a deliberate per-column decision, not a global type-parser override.

- **reset-migrations.ts** — deletes `../../drizzle/` outright. Not a database script: it touches only the generated SQL, and `db:generate` runs it immediately before `drizzle-kit generate --name init` so the generator diffs `schema/` against nothing and emits one baseline. Fixed `--name init` rather than drizzle-kit's random tag (`0000_nasty_silver_centurion`) because the file is regenerated constantly and a name that churns makes every diff look like a new migration.

- **migrate.ts** — runs migrations. Called by `server.ts` at boot; also runnable standalone.

  **`npm run db:migrate` passes `--reset`: it drops every table in `public`, drops drizzle's `drizzle.__drizzle_migrations` bookkeeping schema, and replays from empty.** This is deliberate for the current phase and safe only because no database holds data worth keeping. The reason it is the default rather than an opt-in: the migrator keys on a *hash of each SQL file*, and `db:generate` rewrites that file on every schema edit — a database that applied the previous baseline would read the new one as pending and re-run it against tables that already exist. The two scripts only work as a pair.

  `npm run db:migrate:preserve` is the same script without the flag: apply pending migrations, drop nothing. Under the republish model it is nearly useless — a regenerated baseline is not a diff, so applying it to a populated database fails on the first `CREATE TABLE` — and it exists for the phase after the switch below.

  **Server startup never drops.** `runMigrations()` is the only thing `server.ts` imports; `resetSchema()` is reachable only from the CLI branch, only under `--reset`, and refuses outright when `NODE_ENV=production`. The script prints the target `host:port/database` before dropping, because the failure mode that matters here is a `.env` pointed somewhere other than local Postgres.

  **The switch, when a database first holds real data.** It is one change with three parts, and doing only the first is worse than doing none: keep the current `drizzle/` as the frozen baseline, drop `reset-migrations.ts` from `db:generate` so it appends diffs again, and make `db:migrate:preserve` the default. Until then this is a deliberate arrangement, not a cleanup someone will notice on their own.

- **repositories/** — query logic, one module per table. The domain repositories join the auth ones below.

- **repositories/users.ts** — query logic for `users`. Owns email normalisation (lowercasing) so a caller cannot forget and create a case-duplicate account, and the `deleted_at` filter on the two lookups that could otherwise resolve a request onto a retired account. `createUser` **requires** a `householdId`, with no overload that omits it — go through `households.ts` rather than finding one to pass. `softDeleteUser` is how every account deletion ends — there is no hard delete of a user anywhere in the product.

- **repositories/oauthAccounts.ts** — provider identity links, keyed on the provider's stable subject id rather than email. See `../auth/AUTH_CONTEXT.md`.

- **repositories/authSessions.ts** — refresh-token records and revocation. `getByRefreshHash` deliberately returns revoked and expired rows so the refresh route can tell an unknown token from a replayed one.

- **repositories/households.ts** — the household row, plus the whole account lifecycle that has to move with it. Auto-provisioning lives here, not in the auth routes, so that *no* code path can insert a `users` row without a household.

  - `createUserWithHousehold` — the account-and-household pair, one transaction, used by both sign-up routes. Passing a `household` means the user filled the create form (`skip_household` false); omitting it means they skipped or were never asked (true). Either way they are the household's `admin`, because whoever creates one administers it and the skip case is not special-cased.
  - `createUserInHousehold` — the invitation path, and the **one** route by which a user gets no household of their own. Joins as `user`, `skip_household` false.
  - `updateHousehold` — what "creating a household later" actually is (PRD §2.2.4): a rename of the row the user already has, never an insert. Nothing is ever re-parented.
  - `deletePrivateItemsFor` — every departure path runs this. Here rather than in an inventory repository because it is a membership concern; move it if the inventory module grows a reason to own it.
  - `destroyHousehold` / `deleteAccount` — the asymmetric deletion in PRD §2.2.8, with the last-admin branch decided inside the transaction. `destroyHousehold` destroys what the household owned and re-homes everyone in it — retired members included, since their row still holds the RESTRICT on `users.household_id` — so it is a mass departure, not a mass deletion. Its order is fixed: inventory, then the occupants, then the row.
  - `getMember` — one active member, scoped by household **in the query**, so an id from another household 404s without a second ownership branch a call site can forget. Every member-targeting operation goes through it.
  - `setMemberRole` — PRD §2.3.3, refusing the demotion that would leave a household with zero admins.
  - `removeMember` / `leaveHousehold` — PRD §2.2.10. Both wrap the same private `moveToOwnHousehold`, because removal and leaving are one operation with a different instigator. Only `leaveHousehold` has a last-admin branch: an admin is always left behind by a removal, since the API refuses self-removal.
  - `lockHousehold` — `SELECT … FOR UPDATE` on the household row, taken first by **every** transaction that resolves the "at least one admin" invariant (`setMemberRole`, `leaveHousehold`, `removeMember`, `deleteAccount`). Counting admins and then acting on the count is not atomic on its own: two concurrent demotions of two different admins each see a count of two, each conclude it is safe, and between them leave zero. The household row is the lock object rather than the `users` rows because the membership set is what is changing. **Add this call to any new operation that reads an admin count.**

  Not built here yet: **invitations**. They need a table of its own (a household, an invited email, a single-use token, a 24-hour expiry) and are waiting on both the notifications module and SMTP. Leaving, removal and role changes are done, and their rules live in `../services/households.ts`.

The scoping habit holds one level up: every read on a domain table takes the **household id** as an argument, and there is intentionally no unscoped lookup to reach for. The auth repositories keep taking a user id, because their tables are still user-owned.

The binding rule moves with it. `household_id`, like `user_id` before it, is **resolved server-side from the authenticated session** — never read from a request body and never from an LLM response. The interpreter is handed the household's `{id, name}` category pairs and returns a `category_id`; it is never told the household id and has no way to name one. (`docs/ARCHITECTURE.md` and `CLAUDE.md` still phrase this invariant as "`user_id` is bound server-side" — same rule, pre-household wording.)

## Conventions for new tables

- **App-generated UUID primary keys** via `crypto.randomUUID` rather than a DB-side `gen_random_uuid()`, so no `pgcrypto` extension is needed and the ID is known before the insert returns. Household auto-provisioning depends on this — see *Households*.
- **Every domain table carries `household_id UUID NOT NULL REFERENCES households(id) ON DELETE CASCADE`**, indexed as `(household_id, …)` for its common list query. A new domain table referencing `users(id)` **for ownership** is a bug, not a variation: only `oauth_accounts` and `auth_sessions` are keyed on a user, because they are credentials. The attribution columns in the next bullet are the one other shape allowed to name a user, and they are never filtered on.
- **Attribution is a separate column from ownership.** Where "who did this" is worth keeping — `inventory_items.added_by_user_id` is the only case that exists today — the row carries both `household_id` (the scope every query filters on) and a `NOT NULL … REFERENCES users(id) ON DELETE RESTRICT` (the person, for display only). Mandatory because PRD §2.5.1 makes it so: every item was added by somebody, and it is bound from the session on write and never changed afterwards. `RESTRICT` rather than `CASCADE` or `SET NULL` because **no path in the product hard-deletes a user** — deleting an account is a soft delete and deleting a household re-homes its members (§2.2.8) — so it is a net that never fires rather than a behaviour anything depends on. `CASCADE` would be the specific disaster §2.2.10 rules out: a departing housemate must not delete the household's stock. Never filter on an attribution column; it is provenance, not scope.
- **Privacy is the one exception to that, and it is on `inventory_items` alone.** `is_private` (NOT NULL, default false) makes a row visible only to `added_by_user_id` — PRD §2.2.9, and the single place where an attribution column is load-bearing rather than decorative. Reads must filter `NOT is_private OR added_by_user_id = <caller>`, **including for admins**: the role governs who is in the household and whether it continues to exist, and confers no visibility into another member's things. A private item never outlives its owner's membership — soft delete, leaving and removal all delete these rows rather than leaving the household holding records nobody can read.
- **`jsonb` only for genuinely open-ended fields** (item `attributes`, fallback decisions, notification payloads), validated with zod at the boundary. Anything queried or constrained gets a real column.
- **Anything the app joins on is its own table, not a string column.** `categories` is the worked example (`docs/PRD.md` §5.1.1): budgets aggregate spend by category, so as free text an interpreter writing `grocery` one day and `groceries` the next would silently split a budget with nothing erroring. It carries `UNIQUE (household_id, lower(name))` — a household shares one taxonomy, so two members cannot each create "Groceries" — and both `inventory_items.category_id` and `budgets.category_id` reference it `ON DELETE RESTRICT`, making deletion of a category with items a 409 rather than a cascade that would take a whole collection with it. Apply the same test before adding any other classification column: **does anything join on it, and does drift escape the row?** `inventory_items.unit` fails both, so it stays free text; `households.address` fails both today for the same reason.
